# Ручная проверка. Этап 7 «Деплой»

Что проверяем: бот переехал на сервер и живёт там **сам**, без твоего компьютера.
Критерий приёмки из плана — **бот сутки работает на сервере, и утренний будильник
пришёл вовремя**. Поэтому проверка растянута на два дня: сегодня вечером запускаем
и проверяем, завтра утром смотрим будильник.

Сама установка расписана по шагам в `docs/DEPLOY.md` — этот файл её не заменяет,
а проверяет результат.

Активного времени — минут 30 сегодня и 5 минут завтра. Остальное — ожидание.

---

## ⚠️ Сначала прочитай это, иначе сломается всё остальное

**Бот должен работать ровно в одном месте.** Telegram отдаёт очередь новых сообщений
только одному получателю. Если бот с тем же токеном крутится и на твоём компьютере,
и на сервере, они начнут перехватывать сообщения друг у друга: часть команд не дойдёт,
будильник может не отправиться, а в логах у обоих будет
`Conflict: terminated by other getUpdates request`.

**Перед пунктом 1 найди на своём компьютере окно PowerShell, где запущен `python -m app`,
и нажми в нём Ctrl+C** (или просто закрой окно). Проверь, что таких окон не осталось ни одного,
включая свёрнутые в панель задач.

Дальше на компьютере бота **не запускай вообще** — пока идёт проверка этапа, он должен
жить только на сервере. Если после переезда захочется что-то потестировать локально —
сначала останови серверного: `docker compose down`.

---

## День первый, вечер

### 1. Локальный бот выключен

На своём компьютере в PowerShell:

```powershell
Get-Process python -ErrorAction SilentlyContinue
```

Команда показывает запущенные процессы Python.

**Должно получиться:** пусто (никакой таблицы). Если таблица есть — где-то остался
работающий бот, найди и закрой его окно.

### 2. Пройден `docs/DEPLOY.md`

Пункты 1–17 инструкции сделаны: Docker установлен, репозиторий склонирован,
`.env` заполнен, `docker compose up -d --build` отработал.

Если ещё нет — иди в `docs/DEPLOY.md` и вернись сюда после пункта 17.

### 3. Контейнер запущен

На сервере, из папки проекта (`cd tg-schedule-bot`):

```
docker compose ps
```

**Должно получиться:** одна строка `tg-schedule-bot`, в колонке `STATUS` — `Up ...`.

Чего быть **не** должно: `Restarting` (бот падает по кругу) или `Exited` (упал совсем).
В обоих случаях — `docker compose logs --tail 100` и в Claude Code.

### 4. В логе московское время и все три планировщика

```
docker compose logs --tail 30
```

**Должно получиться:** строки

```
Бот запущен: @имя_твоего_бота (id=...)
Планировщик будильников запущен, пересчёт каждый день в 05:00 по Москве
Планировщик заметок запущен, пересчёт каждый день в 05:00 по Москве
```

**И главное — время в начале строк.** Посмотри на часы на телефоне (московские).
Время в логе должно совпадать с точностью до минуты. Если оно отстаёт на 3 часа —
контейнер живёт по UTC, зона не подхватилась: скопируй лог в Claude Code, это ошибка,
дальше идти нельзя. Именно от времени зависит, во сколько сработает будильник.

Дополнительная проверка того же самого, если хочется убедиться наверняка:

```
docker compose exec bot python -c "from app.clock import now; print(now())"
```

Команда запускает одну строчку кода **внутри** работающего контейнера и печатает
«сейчас» так, как его видит бот.

**Должно получиться:** дата и время, совпадающие с московскими, и хвост `+03:00`.

### 5. Бот отвечает в Telegram

Напиши боту по очереди:

| Команда | Что должно прийти |
|---|---|
| `/start` | приветствие или вопросы онбординга (база на сервере новая, пустая) |
| `/today` | пары на сегодня или честное «сегодня пар нет» |
| `/tomorrow` | пары на завтра |
| `/route` | время в пути до ближайшего корпуса |
| `/preview` | во сколько бот разбудит завтра и почему |
| `/notes` | список заметок или «пока пусто» |

Если `/start` спрашивает геопозицию — пройди онбординг до конца: без него не будет
ни адреса, ни времени на сборы, а значит и будильника завтра тоже не будет.

**Должно получиться:** ответ приходит на каждую команду, без задержек в минуты.

### 6. Данные переживают перезапуск контейнера

Это проверка, что база лежит на сервере, а не внутри контейнера.

```
docker compose down && docker compose up -d
```

Первая часть останавливает и **удаляет** контейнер, вторая создаёт новый.

Подожди секунд двадцать и напиши боту `/settings`.

**Должно получиться:** бот помнит твой адрес, транспорт, время на сборы — всё, что ты
вводил в пункте 5. Если он снова здоровается как с новым человеком — база не сохранилась,
это ошибка, зови Claude Code.

Заодно проверь, что файл базы виден с сервера:

```
ls -lh data
```

**Должно получиться:** в списке есть `bot.db` (и, возможно, `bot.db-wal`, `bot.db-shm` —
это его рабочие спутники, так и должно быть), а также `schedule_4md4.json`.

### 7. Бот переживает перезагрузку сервера

Самая важная проверка «живучести»: сервер могут перезагрузить без тебя (обновления,
сбой у провайдера), и бот обязан подняться сам.

```
reboot
```

Перезагружает сервер. Твоё SSH-соединение при этом оборвётся — появится
`Connection to ... closed by remote host`. Это нормально.

Подожди минуту-две, подключись заново и проверь:

```powershell
ssh root@ТВОЙ_IP
```

```
cd tg-schedule-bot && docker compose ps
```

**Должно получиться:** `STATUS` снова `Up ...` — контейнер поднялся сам, без единой
твоей команды. За это отвечает `restart: unless-stopped` в `docker-compose.yml`.

Для верности напиши боту `/today` — должен ответить.

### 8. Резервная копия базы делается

```
bash scripts/backup_db.sh
```

**Должно получиться:** строка `... копия готова: /root/tg-schedule-bot/backups/bot-ДАТА-ВРЕМЯ.db`

```
ls -lh backups
```

**Должно получиться:** файл `bot-...db` размером хотя бы несколько десятков килобайт
(не 0 байт).

### 9. Ночной бэкап поставлен в расписание

```
crontab -l
```

Печатает список задач по расписанию.

**Должно получиться:** видна строка, начинающаяся с `0 3 * * *` и заканчивающаяся
на `backup_db.sh ...`. Если пусто — вернись к пункту 16 в `docs/DEPLOY.md`.

### 10. Проверь `/preview` перед сном

```
/preview
```

**Должно получиться:** бот пишет, во сколько разбудит завтра, до какого корпуса ехать
и почему именно так.

Отдельно посмотри на ответ:

- Если завтра **понедельник** или день без очных пар — бот честно скажет, что будильника
  не будет. Это правильное поведение, но для приёмки этапа тогда нужен другой день:
  дождись ближайшего дня с очной парой (по числителю пары есть во вторник, среду,
  пятницу и субботу; по знаменателю — во вторник, среду и четверг).
- Запиши себе время подъёма, которое назвал `/preview`. Завтра сверим.

**Отключись от сервера** (`exit`) и **не включай бота на компьютере**.

---

## День второй, утро

### 11. Будильник пришёл вовремя

**Должно получиться:** утром в Telegram лежит сообщение от бота с временем выхода,
временем в пути и первой очной парой. Время прихода сообщения совпадает с тем,
что вчера показал `/preview` (расхождение в несколько минут нормально: бот пересчитывает
пробки в момент отправки, поэтому подъём может немного сдвинуться).

Это и есть главный критерий приёмки этапа 7.

Если пробки посмотреть не удалось, бот всё равно должен разбудить — по запасной оценке,
с честной оговоркой в тексте. Такое сообщение тоже считается успехом.

### 12. Бот отработал сутки без перезапусков

```
docker compose ps
```

**Должно получиться:** в колонке `STATUS` — `Up 20 hours` или похожее время
**больше суток от момента запуска**. Если там `Up 5 minutes`, значит, бот за ночь падал
и перезапускался: смотри `docker compose logs --tail 200` и ищи строки со словом
`Traceback` или `аварийно`.

### 13. Ночной бэкап отработал сам

```
cat logs/backup.log
```

**Должно получиться:** строка с сегодняшней датой и текстом `копия готова: ...`.

```
ls -lh backups
```

**Должно получиться:** копий стало больше на одну.

### 14. В логе за ночь нет ошибок

```
docker compose logs --tail 200 | grep -i "error\|traceback\|conflict"
```

Команда показывает только строки, где встречается «error», «traceback» или «conflict».

**Должно получиться:** пусто или одна-две строки про неудачный запрос к 2ГИС
(это штатная ситуация: бот в таком случае будит по запасной оценке).

Если попадается `Conflict: terminated by other getUpdates request` — где-то всё-таки
работает второй экземпляр бота. Проверь свой компьютер (пункт 1) и телефон коллег
по группе, если вы запускали бота вдвоём.

---

## Итог: этап 7 принят, если

- [ ] на компьютере бот выключен, работает только серверный;
- [ ] `docker compose ps` показывает `Up` больше суток;
- [ ] время в логе — московское;
- [ ] бот отвечает на команды в Telegram;
- [ ] после `docker compose down` + `up -d` настройки на месте;
- [ ] после перезагрузки сервера бот поднялся сам;
- [ ] **утренний будильник пришёл вовремя**;
- [ ] в `backups/` лежит копия, созданная ночью по расписанию.

Это последний этап плана. После него проект можно считать законченным: дальше —
только правки по мере жизни (новое расписание от деканата, новые пожелания).

---

## Если что-то не сошлось

Разделы «Если что-то не так» в `docs/DEPLOY.md` (пункты 21–23) разбирают частые случаи:
контейнер в `Restarting`, неверный токен, нет доступа к Telegram, конфликт двух ботов,
нет прав на папку с базой.

Если там не нашлось — собери в чат Claude Code сразу три вещи:

```
docker compose ps
docker compose logs --tail 100
tail -n 100 logs/bot.log
```

и напиши: `Используй агента debugger. Проверяю этап 7, вот что происходит: <вставь вывод>`.

Токен и ключи из `.env` в чат не вставляй.
